# Documents
Upload validates type, magic bytes and size, rejects duplicate content (SHA-256), stores bytes via `ObjectStorage` (local FS) and runs the extractor chain:
1. `PdfTextExtractor` - born-digital PDFs only, via poppler `pdftotext` (fixed argv, no shell, timeout, output cap).
2. `PlainTextExtractor` - text/plain and text/csv.

**There is no OCR.** Scans, photos, corrupt/encrypted PDFs, and a missing `pdftotext` all end as REVIEW_REQUIRED with a reason and no extraction row. Even successful extraction only stores text for a person to read; nothing creates invoices/rates/manifests.

Manual fallback: enter the data in the normal forms and pick the **Source document** (marks it PROCESSED automatically), or use "Mark as manually processed" (`POST /documents/:id/resolve`, only from REVIEW_REQUIRED/FAILED).

## Invoice candidates (Step 15a, read-only)
`GET /api/v1/documents/:id/invoice-candidates` (ViewData) reads the document's stored extraction text with a deterministic, versioned rule-based parser (`extraction::invoice_parser`, `parser_version` in every response, currently `invoice-rules-3`) and returns *candidate* invoice fields for a person to review. It is advisory only:
- **Read-only.** It inserts nothing, changes no document status, creates no invoice or vendor, and feeds nothing to reconciliation. Candidates are computed on demand from the stored text, so the same document always gives the same output.
- **Fields:** vendor, invoice number, invoice date, service date, waste stream, invoice total, and line items (description, fee code, quantity, unit, unit price, line total). Each value is `extracted`, `uncertain` (ambiguous, malformed, conflicting, or failing a check; `reasons` and `alternatives` say why) or `missing`, with the source line as `evidence`. There is deliberately **no confidence score**: a value that looks right is not proof that it is right.
- **Never guessed:** fee codes come only from an explicit fee-code column (a blank fee code is priced as a *disposal* line, so every blank-fee-code line is listed in `acknowledgments_required`); the service date is never defaulted from the invoice date; unreadable amounts/dates get no value; contract rates are never involved; a vendor is only *suggested* on an exact (case-insensitive, trimmed) name match and never created.
- **Nothing is silently dropped:** table rows the parser cannot read, lines OUTSIDE the table that end in an amount (before or after it; two-column rows, whole-number amounts and `$`-prefixed amounts included), and every tax row are returned in `unparsed_lines`, each with a `kind` (`unreadable_row`, `unreadable_amount`, `charge_like`, `possible_charge`, `tax`, `subtotal`) and a reason. A trailing token that LOOKS like an amount but cannot be read (`$4,50.00`, `4.500,00`, `12O0.00`) is kept as `unreadable_amount` with its original text, never dropped for failing to parse (the same holds for tax and subtotal rows). A bare whole number in its own column is flagged as `possible_charge` because it may be a charge or an address/phone/reference number: the parser cannot tell, so it says so. The list is capped at 500; the remainder is counted in `unparsed_not_listed`.
- **Subtotals and tax:** a subtotal row is accounted for (and not listed) only when it equals a COMPLETE parsed line sum (every line total readable, nothing charge-like left over), wherever it appears. Tax rows are never accounted for: they stay listed with their amount, they make the invoice total differ from the lines (flagged on the total), and they keep `line_sum_complete` false until a person represents the tax.
- **`checks.line_sum_complete` means positive evidence, not readable rows:** a table was recognised, every line total is readable, no unreadable row / charge-like line / tax row / unaccepted subtotal remains, AND the sum is corroborated by a single matching invoice total or an accepted subtotal. When false, `checks.incompleteness_reasons` says why; when true, `checks.completeness_basis` says what the evidence was. A truncated extraction is never complete. Even when true it is evidence for a reviewer, not a verdict that the invoice is correct.
- **Responses:** `409` for a non-INVOICE document or one with no extracted text (scans, images: enter the invoice manually); `404` for another tenant's or an unknown document. `reviewable` is false once the document is linked to an invoice (`linked_invoice_id`).
- **`confirmation_requirements` (Step 15b-3, additive):** the acknowledgments a later confirmation must carry, derived by the server and never by the client: the parser's own `acknowledgments_required`, plus `unparsed_lines[N]` for each listed unparsed line (N = 1-based text line), `unparsed_not_listed`, `text_truncated` and `line_sum_incomplete`; `original_document_check_required` is true when any of the last three applies. The `candidates` object and `parser_version` are unchanged.
- **Limits:** tuned on synthetic layouts only, not validated against real vendor invoices. Single invoice per document; labels must start a layout column; wrapped descriptions, merged cells and tables with 2+ spaces inside a cell are returned as unparsed lines. Scanned documents still require manual entry; there is no OCR.
