# API (all under /api/v1, JSON, `Authorization: Bearer <session>` except health/auth/webhook)
Auth: `POST /auth/signup|login|logout`, `GET /me`. Data: `/vendors`, `/contracts` (+`/contracts/:id/rates`, `PUT /rates/:id/end`, `PUT /rates/:rate_id/fees/:fee_code/type`), `/invoices` (+`PUT /invoices/:id/manifest`), `/manifests`, `/weight-tickets` (GET list/detail, POST create). Documents: `POST /documents?document_type=&filename=` (raw body, `Content-Type` = file type), `GET /documents[/:id[/download]]`. Workflow: `POST /reconciliations/run`, `GET /reconciliations[/:id]`, `GET /discrepancies[?status=]`, `POST /discrepancies/:id/review {action,notes}`, `GET|POST /discrepancies/:id/evidence`, `GET /discrepancies/:id/evidence/pdf`, `GET|POST /disputes`, `POST /disputes/:id/transition {to,amount?,credit_memo_reference?}`, `GET /recovery`, `GET /dashboard`. Admin: `GET|POST /members`, `GET /audit`, `GET /notifications`, `POST /notifications/:id/read`, `POST /monitoring/run`, `GET /monitoring/jobs`, `GET /billing/status`, `GET /billing/checkout-context` (OWNER/ADMIN), `POST /billing/paddle/webhook` (signature-authenticated), `POST /documents/:id/resolve`.
Errors: `{"error":{"code","message"}}` with 400/401/402/403/404/409/413/422/503. Money/quantities: send decimal strings; receive 4-decimal strings. Reconciliation responses include `pricing_status` (`COMPLETE`, `PARTIAL`, `UNCOMPUTABLE`, or `LEGACY_UNVERIFIED`). For non-complete pricing, `expected_amount` and bill-level `discrepancy_amount` are `null`; partial results may include `partial_expected_amount`, which is only a diagnostic subtotal. `identified_finding_amount` sums amounts attached to findings and must not be interpreted as total invoice exposure when pricing is incomplete.

## Authorized fees and charge types
`POST /contracts/:id/rates` takes `authorized_fees: [{fee_code, description?, amount, charge_type}]`. `charge_type` is **required** and must be exactly `"EXACT"` or `"CAP"` (upper case); `amount` must not be negative. A missing, `null`, non-string, differently-cased, padded or unknown `charge_type` is rejected before anything is written with **422** `{"error":{"code":"UNPROCESSABLE_ENTITY","message":"..."}}` (message names the fee code). Other validation problems keep the existing 400 `VALIDATION_ERROR`. Contract and rate responses (`GET /contracts/:id`, create and end responses) list each fee as `{fee_code, description, amount, charge_type}`; `charge_type` is `null` for a legacy unclassified fee.

`PUT /rates/:rate_id/fees/:fee_code/type` classifies a legacy fee. Body: `{"charge_type": "EXACT" | "CAP"}` (only that field; same value rules as above). `:fee_code` is matched exactly (case-sensitive, after trimming) against the fee stored on that rate.
- **Permission:** `ManageData` (OWNER, ADMIN and MEMBER; a REVIEWER gets 403). Not subject to the billing entitlement check.
- **200:** the updated contract detail (same shape as `GET /contracts/:id`) with the fee's new `charge_type`.
- **Classify once:** only while `charge_type` is `NULL`. A classified fee is immutable: any further request, including the same value, returns **409** `CONFLICT` ("already classified as X ... requires a new rate version"). A different meaning requires a new rate version; there is no edit path. A database trigger enforces this independently.
- **404** `NOT_FOUND` for an unknown rate or fee code, and for another organization's rate (indistinguishable). **401** without a session. **403** without `ManageData`. **400** `VALIDATION_ERROR` for an empty or over-long (over 50 characters) `fee_code`.
- **422** `UNPROCESSABLE_ENTITY` (application envelope) when `charge_type` is missing, `null`, not a string, or not exactly `EXACT`/`CAP`.
- **Malformed requests are not in the application envelope.** Axum rejects them before the handler with a plain-text body: invalid JSON or an empty body gives 400, an unknown extra field gives a plain-text **422**, a missing `Content-Type: application/json` gives 415, and a non-UUID `:rate_id` gives 400. To tell the two 422s apart, check for the JSON `error.code` of `UNPROCESSABLE_ENTITY`.
- **Audit:** one record, action `contract_authorized_fee.classify`, resource `contract_authorized_fee` (the fee's id), `before_state` `{"charge_type": null}`, `after_state` with `charge_type`, `fee_code`, `contract_rate_id`, `classified_by` and `classified_at`; the actor and time are also stored on the fee (`charge_type_set_by`, `charge_type_set_at`).
- **Effect on reconciliations:** existing reconciliations and evidence are never rewritten. In the same transaction the endpoint records a durable re-reconciliation request for each invoice the fee can price (same organization, vendor and waste stream, service date inside the rate's window, invoice bills the fee code); the monitoring worker (or `POST /reconciliations/run`) then reconciles those invoices once (see `reconciliation.md`). The response is unchanged.

Evidence (`POST|GET /discrepancies/:id/evidence`) includes `charge_type` on each fee in `contract_rate.authorized_fees` (`null` = unclassified; absent in packages stored before charge types). For invoices priced by several rates `contract_rate` is `null` (no parent rate is invented) and the package carries `applicable_rates[]` (each rate with its `authorized_fees[]` and `priced_line_ids[]`), `fee_lines[]` (per billed fee line: `authorizations[]`, `priced_by_contract_rate_id`, `expected_line_amount`) and `applicable_rates_basis` (`recorded`, including an empty recorded set; `line_rates_only` or `none` only for reconciliations made before the set was recorded); these keys are additive and absent from packages stored earlier. See `reconciliation.md`. Reconciliation responses may contain findings `RULE_11_AMBIGUOUS_FEE`, `RULE_12_UNCLASSIFIED_FEE_TYPE` and `RULE_13_UNRECONCILED_BILL_TOTAL` (amount `0.0000`), which come with `pricing_status` `PARTIAL`. Finding amounts are `billed - expected`, so a finding amount can be negative; negative findings are excluded from dashboard and recovery totals and cannot be disputed (409).
