# Build Notes — current state (read before continuing)

## Toolchain and operational requirements
- Rust **1.75.0** (apt) with exact-pinned dependencies in `backend/Cargo.toml`/`Cargo.lock`; always build with `--locked`. A current toolchain (1.80+) can probably relax the pins — re-run the whole suite if you try. `cargo build --release` takes ~10 minutes: run it detached or with a long timeout.
- **No database is needed to compile.** All SQL is runtime-checked. **Tests do need a database**: set `DATABASE_URL` to the least-privilege role (`xflow_app`) on a migrated database, because the integration tests exercise RLS through that role.
- **System tools**: `pdftotext` (poppler-utils) reads the text layer of PDFs — installed in the backend Docker image; without it PDFs fall back to manual entry. `qpdf` is optional (extra PDF validation in tests). Tests that need these tools skip their external assertions if missing.
- Migrations: `MIGRATION_DATABASE_URL=<privileged role> sh scripts/migrate.sh` (tracked in `schema_migrations`, idempotent). Migration 0002 creates `xflow_app` with the placeholder password `CHANGE_ME_IN_PRODUCTION`: set `XFLOW_APP_PASSWORD` in any real environment. **Caution: roles are cluster-wide — never run `migrate.sh` with `XFLOW_APP_PASSWORD` against a scratch database on a cluster whose `xflow_app` you care about.** 0001/0002 are never edited; 0003 (workflow support, monitoring job functions) and 0004 (case-insensitive email) are additive.
- Env: see `.env.example`. Web runtime env: `API_INTERNAL_URL`, `PADDLE_CLIENT_TOKEN`, `PADDLE_PRICE_ID`, `PADDLE_ENV`, `INSECURE_COOKIES=1` (only for local http testing of a production build).
- Opaque sessions, not JWT (revocation). Unchanged.

## Known limitations — not hidden
- **Paddle.js is stubbed in the browser test** (cdn.paddle.com is not reachable from the sandbox and a real checkout needs a card). Verified: our code calls `Paddle.Environment.set/Initialize/Checkout.open` with the right arguments, and the webhook handling is verified with correctly signed simulated events. **Not verified against a real Paddle sandbox account** (event payload shapes follow Paddle Billing's documented format but could differ in edge cases).
- A customer who buys a second subscription while one is active is not auto-reconciled (event is stored with an error note and ignored); handle manually.
- No OCR; no S3-compatible storage (only local FS); PDF evidence is plain text (no logo/layout styling, ASCII only).
- No login rate limiting / brute-force lockout, per-IP rate limiting, password reset, email verification, MFA, or email delivery of notifications.
- Sessions pick the user's oldest membership; no multi-organization users/org switching.
- Frontend lists show the first 100–200 rows (no pagination UI). The e2e test covers one customer path; it is not exhaustive UI coverage.
- **Docker images, docker-compose and the GitHub Actions workflow were never executed** (no Docker/GitHub in the sandbox). What WAS exercised instead: the backend release build from the locked sources; `npm ci` from `package-lock.json` + production build + the standalone `server.js` runtime layout used by `Dockerfile.web`; the compose `migrate` entrypoint layout against a scratch database; YAML syntax of compose and CI. Treat the first CI/Docker run as the real verification.
- ICP, pricing and go-to-market remain proposals, not implemented decisions.
